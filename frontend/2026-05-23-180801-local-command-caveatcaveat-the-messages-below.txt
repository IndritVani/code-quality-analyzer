     Code Quality Analyzer — Backend Build Plan

     Context

     We're building the backend of the Code Quality Analyzer described in
     C:\Users\vanii\Downloads\SPEC.md: a Spring Boot service that walks a local
     Java repo, parses each .java file into an AST, computes a suite of quality
     metrics, persists them to PostgreSQL at file + project granularity, and
     exposes a REST API. This is an academic tool for reproducible cross-project
      code-quality comparison.

     Decisions made with the user:
     - Backend-first vertical slice — full backend (entities, analyzer engine +
     all 7 metrics, REST API, persistence) running and analyzing a real repo via
      curl, before the React dashboard (a later pass).
     - PostgreSQL via Docker — matches spec; a docker-compose.yml spins up
     Postgres 15, no local install.
     - Node deferred — only needed for the frontend phase; user will install
     Node 18+ then.

     Toolchain reality: Java 21 ✅, git ✅, Docker ✅. Maven, Node, Postgres ❌
     not installed. Backend therefore uses the Maven wrapper (mvnw) so no global
      Maven is required, and Docker hosts Postgres.

     Spec discrepancies found (and how this plan handles them):
     1. The Data Model defines only file_metrics and project_metrics tables, but
      §3 mentions a third "module level". → Persist file + project (the defined
     schema); expose module-level as a derived view (group file metrics by
     package) — no extra table.
     2. Duplication Ratio, Dependency Health, and Maintainability Index aren't
     AST-per-file metrics and need concrete definitions. → Specified below as
     documented heuristics.
     3. "Outdated/vulnerable dependency" detection is inherently
     network-dependent. → Best-effort Maven Central version check, never fails
     the run; clean extension point left for a real CVE source.

     ---
     Project location & scaffolding

     Create C:\Users\vanii\code-quality-analyzer\backend\. git init at the
     project root with a Java/Node .gitignore.

     Bootstrap the Spring Boot project via Spring Initializr (gives us
     mvnw/mvnw.cmd + base pom.xml + main class without a local Maven):

     curl https://start.spring.io/starter.zip \
       -d type=maven-project -d language=java -d javaVersion=21 \
       -d bootVersion=3.4.x -d groupId=com.analyzer -d artifactId=analyzer \
       -d name=analyzer -d packageName=com.analyzer \
       -d dependencies=web,data-jpa,postgresql,validation \
       -o starter.zip   # then unzip into backend/

     Then add JavaParser to pom.xml:
     <dependency>
       <groupId>com.github.javaparser</groupId>
       <artifactId>javaparser-core</artifactId>
       <version>3.25.9</version>
     </dependency>

     No Lombok — use Java records for DTOs and plain classes for JPA entities to
      minimize moving parts.

     ---
     Package layout (com.analyzer)

     Matches SPEC §"Project Structure":

     api/         ProjectController, AnalysisController, ComparisonController
     service/     ProjectService, AnalysisService (@Async run orchestration)
     analyzer/    AnalyzerEngine (pipeline orchestrator)
       pipeline/  FileDiscovery, ResultAggregator, ResultPersister
       metrics/   MetricExtractor (iface), FileMetricResult (accumulator),
                  LocExtractor, CyclomaticComplexityExtractor,
                  CouplingExtractor, CommentDensityExtractor,
                  DuplicationAnalyzer, DependencyHealthAnalyzer  (project-level,
      not the iface)
     domain/      Project, AnalysisRun, ProjectMetrics, FileMetrics, enums Tier
     + RunStatus
     repository/  one Spring Data JPA repo per entity
     dto/         CreateProjectRequest, ProjectResponse, RunResponse,
                  FileMetricsResponse, ComparisonResponse

     ---
     Domain / persistence

     JPA entities mirror the Data Model tables exactly (UUID PKs, the listed
     columns). Enums: Tier {WELL_MAINTAINED, AVERAGE, NEGLECTED}, RunStatus 
     {PENDING, RUNNING, COMPLETE, FAILED}. application.yml per spec (Postgres
     datasource, ddl-auto: update, port 8080). Hibernate auto-creates the schema
      on first run.

     ---
     Analyzer engine (the core)

     Pipeline in AnalyzerEngine, matching SPEC §"Implementation Detail":
     ProjectPath → FileDiscovery → JavaParser → MetricExtractors[] → 
     ResultAggregator → ResultPersister.

     - FileDiscovery — Files.walk the project path, collect .java files (skip
     target/, build/, .git/).
     - Parse — StaticJavaParser.parse(file) → CompilationUnit per file. Parse
     failures are caught per-file and skipped (logged), so one bad file doesn't
     fail the run.
     - MetricExtractor interface — exactly as in spec: String getMetricName(); 
     FileMetricResult extract(CompilationUnit ast, Path filePath);. Each
     per-file extractor sets only its own fields on a FileMetricResult; the
     engine merges the partial results into one FileMetricResult per file.

     Per-file AST extractors (implement the interface):

     ┌───────────────────────────────┬──────────────────────────────────────────
     ┐
     │           Extractor           │                 Approach
     │
     ├───────────────────────────────┼──────────────────────────────────────────
     ┤
     │ LocExtractor                  │ Raw LOC = total lines; effective LOC =
     │
     │                               │ non-blank, non-comment lines.
     │
     ├───────────────────────────────┼──────────────────────────────────────────
     ┤
     │                               │ Per method: 1 + count of
     │
     │ CyclomaticComplexityExtractor │ if/for/while/do/case/catch/&&/||/?:.
     │
     │                               │ Aggregate avg + max per file.
     │
     ├───────────────────────────────┼──────────────────────────────────────────
     ┤
     │                               │ Count distinct external type references
     │
     │ CouplingExtractor             │ per class (field/param/return/local
     │
     │                               │ types, minus java.lang + self-package).
     │
     ├───────────────────────────────┼──────────────────────────────────────────
     ┤
     │                               │ (Javadoc + line + block comment lines) ÷
     │
     │ CommentDensityExtractor       │  LOC, via
     │
     │                               │ CompilationUnit.getAllComments().
     │
     └───────────────────────────────┴──────────────────────────────────────────
     ┘

     Project-level analyzers (not the per-file interface):
     - DuplicationAnalyzer — normalize lines (trim), sliding 6-line windows
     hashed across all files; duplication ratio = duplicated lines ÷ total
     lines. A documented CPD-lite heuristic.
     - DependencyHealthAnalyzer — parse pom.xml <dependencies>; count total;
     best-effort query Maven Central (search.maven.org) for latest version to
     flag outdated. Network errors → outdated count 0, run still succeeds.
     Extension point for a real CVE feed.

     ResultAggregator — rolls file results into project totals/averages, then
     computes the Maintainability Index as a documented 0–100 composite
     (transparent weighted blend; higher is better):
     MI = clamp(0,100,
           100
           - 0.40 * min(avgCyclomatic, 25) / 25 * 100   // complexity penalty
           - 0.25 * duplicationRatio * 100              // duplication penalty
           - 0.20 * min(avgCoupling, 20) / 20 * 100     // coupling penalty
           + 0.15 * min(commentDensity, 0.30) / 0.30 * 100 ) // doc bonus
     Weights documented in code so the score is reproducible/defensible. Module
     level = derived by grouping file metrics by package (API/dashboard concern,
      not persisted).

     ResultPersister — writes one project_metrics row + N file_metrics rows for
     the run.

     Execution model — POST /analyze creates an AnalysisRun (PENDING), kicks off
      an @Async method that flips it to RUNNING, executes the pipeline, sets
     COMPLETE (or FAILED + error_message), and returns the run id immediately.
     Client polls GET /api/runs/{runId} — matches the spec's "polling is
     sufficient" + run-status enum.

     ---
     REST API (all endpoints from SPEC §"API Endpoints")

     Projects: GET/POST /api/projects, GET/DELETE /api/projects/{id}.
     Analysis: POST /api/projects/{id}/analyze, GET /api/projects/{id}/runs, GET
      /api/runs/{runId}, GET /api/runs/{runId}/files.
     Comparison: GET /api/compare?ids=....
     DTOs are Java records; controllers thin, delegating to services.

     ---
     Tests

     spring-boot-starter-test (JUnit 5). Unit test per AST extractor (the spec's
      emphasis): feed small hardcoded Java snippets through
     StaticJavaParser.parse(String) and assert metric values (e.g. a method with
      two ifs → cyclomatic 3). Plus one @SpringBootTest slice for
     AnalysisService against an embedded/H2 or Testcontainers Postgres if quick;
      otherwise manual end-to-end via curl (below).

     ---
     Build order (execution)

     1. Scaffold via Initializr, add JavaParser, docker-compose.yml, .gitignore,
      git init.
     2. Domain entities + enums + repositories + application.yml.
     3. MetricExtractor iface + FileMetricResult + FileDiscovery.
     4. Four AST extractors — each with its unit test as it's written.
     5. DuplicationAnalyzer, DependencyHealthAnalyzer.
     6. ResultAggregator (incl. MI) + ResultPersister.
     7. AnalyzerEngine + AnalysisService (@Async) + ProjectService.
     8. Controllers + DTOs.
     9. End-to-end verification.

     ---
     Verification (end-to-end, no frontend)

     1. docker compose up -d → Postgres 15 on 5432 (db code_analyzer).
     2. cd backend && ./mvnw spring-boot:run (first run downloads Maven + deps).
     3. ./mvnw test → all extractor unit tests green.
     4. Clone a known repo locally, e.g. git clone 
     https://github.com/spring-projects/spring-petclinic (well-maintained tier
     from the spec's dataset).
     5. Register + analyze + poll via curl:
     POST /api/projects            {name, path:<petclinic abs path>,
     tier:"well_maintained"}
     POST /api/projects/{id}/analyze   → returns runId
     GET  /api/runs/{runId}            → poll until status=complete, inspect
     project_metrics
     GET  /api/runs/{runId}/files      → spot-check per-file metrics
     6. Sanity-check the numbers (petclinic should score high MI, low
     duplication, healthy comment density). Optionally register a messier repo
     and confirm GET /api/compare?ids=... returns a sensible side-by-side.

     Once the backend is validated this way, we start the React/Vite dashboard
     pass (you install Node first).
